No ledger or payment adapter is required for phase 3.

**Smallest interface:** a thin session-bound read/write adapter in `backend/payroll-costing/src/repositories/rules.py` and `periods.py`; accept an existing `sqlalchemy.orm.Session`, validated tenant/actor/role from the shared auth boundary, and contract-shaped `FinancialRuleRequest`, `FinancialRuleApproval`, `PeriodRequest`/`PayrollPeriodStatus`. Reuse `propose_rule`, `assert_may_propose`, `assert_may_approve` in `src/services/financial_rules.py:22-49`, `create_period`, `assert_transition_allowed` in `src/services/payroll_periods.py:36-67`, and `require_approved` in `src/services/rule_gate.py:35-53`. Suggested narrow signatures: `list_financial_rules(db: Session, tenant_id: UUID) -> list[FinancialRule]`; `get_required_versions(db: Session, tenant_id: UUID, rule_names: Sequence[str], on_date: date) -> list[RuleReference]`; `propose_financial_rule(db: Session, tenant_id: UUID, actor_id: UUID, role: str, request: FinancialRuleRequest) -> FinancialRule`; `approve_financial_rule(db: Session, tenant_id: UUID, actor_id: UUID, role: str, rule_id: UUID, approval: FinancialRuleApproval) -> FinancialRule`; `create_payroll_period(db: Session, tenant_id: UUID, request: PeriodRequest) -> Period`; `list_payroll_periods(db: Session, tenant_id: UUID) -> list[Period]`; `transition_period(db: Session, tenant_id: UUID, period_id: UUID, expected: PayrollPeriodStatus, target: PayrollPeriodStatus) -> None`. These are **recommendations, not existing functions**. Do not add separate typed protocols or repository base classes unless a real second implementation requires them. Do not expose HTTP routes yet.

**Boundary:** caller owns one session/transaction for tenant context, idempotency reservation, SQL change and response completion; repository never commits/rolls back or opens a second session. If a rollback occurs, transaction-local context must be reinstalled before subsequent SQL. SQLAlchemy 2.0 transaction guide confirms autobegin, `Session.begin()` commit/rollback context, and that `Session.commit()` commits the *outermost* transaction: https://docs.sqlalchemy.org/en/20/orm/session_transaction.html . Do not invent that mapping: stop for owner decision or document a separately approved internal derivation before writes.

**Blocking static findings requiring migration revision before phase-3 persistence:** M012 `payroll_rule_approval_guard` requires `Owner` on **INSERT** (:287-294), but frozen OpenAPI `proposeFinancialRule` authorizes both Owner and FinancePayroll (`contracts/openapi.yaml:1037-1052`) and pure service agrees (`financial_rules.py:19-29`). Narrow fix: permit `PENDING` INSERT for the two allowed roles while keeping `Owner`, actor match and evidence mandatory for UPDATE to `APPROVED`; test Finance proposal + Finance approval denied + Owner approval accepted. M012 grants INSERT but no direct SELECT; ordinary INSERT `RETURNING *` or UPDATE `RETURNING *` may fail for `lukla_app`; use known IDs plus checked read after write, or narrowly scoped owner-executed function only if the restricted-role regression proves it necessary. M012 `GRANT UPDATE ON payroll_periods` while SELECT is revoked (:539-565); a direct `UPDATE ... WHERE status = :expected RETURNING ...` may need additional SELECT rights. Test a restricted-role update, and if blocked use a **narrow checked transition routine** rather than restoring blanket SELECT. Pending-rule `409` + `PENDING_RULE` state is not a single transaction on SQL exception: M012 calculation comments require recording status in a separate transaction (:363-367). This is later calculation behavior, **not phase-3 permission to persist money**; preserve the gate and verify no money inserted.

**Other contract mismatch:** M009 period table checks only `period_start < period_end` and uniqueness for identical ranges (`009_payroll_core.sql:41-59`); it does **not** enforce `Asia/Jakarta`, cutoff seconds `:00`, or overlapping nonidentical windows. `PeriodRequest` enforces timezone/cutoff format (`src/models/payroll_period.py:13-39`); `assert_valid_period_range` enforces exclusive end (`src/services/payroll_periods.py:52-55`). To make direct SQL respect the contract add narrowly scoped DB checks for timezone and cutoff, and decide with owner whether overlapping windows are forbidden (technical plan raises overlap as an edge, but frozen contract does not specify overlap exclusion). Do not silently add a blocking overlap constraint as new policy. `financial_rule_versions` has `approved_by` and `evidence_file_id` (`009_payroll_core.sql:3-19`), contradicting the stale comment in `src/services/financial_rules.py:44-49`; no new table is needed. SQL trigger restricts APPROVED update to Owner and evidence (`012_payroll_routines_rls.sql:287-309`); enforce nonempty/nonzero UUID evidence upstream as contract requires and test direct SQL bypass attempts.
