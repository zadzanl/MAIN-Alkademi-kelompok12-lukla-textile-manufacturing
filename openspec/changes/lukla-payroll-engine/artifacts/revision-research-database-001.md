## Findings — source-verified, runtime not rerun

1. **Phase 1/3 persistence absent [Verified source; blocker].** Inventory of `backend/payroll-costing/src/` has models, pure services and empty `api/__init__.py`, but no `repositories/` or `adapters/` directory. `services/financial_rules.py:22-51` creates/approves copies with no DB call and delegates evidence validation to an unimplemented API. `services/payroll_periods.py:40-73` guards pure transitions but writes no rows. Existing `tests/test_financial_rules_service.py:1-75` and `tests/test_payroll_period_models.py:1-57` exercise pure behavior/models, not DB state or retry. Thus do not mark phase 1 typed adapters or phase 3 persistent rule/period seam passed. Existing shared `backend/app/core/database.py:69-83` transaction-local context adapter and `backend/app/services/idempotency.py:25-110` reserve/replay pattern exist, but they do not implement payroll repositories. Preserve Python pure services and avoid a fake router or new dependency.
2. **Rule proposal role mismatch [Verified source; predicted runtime failure].** Contract/tasks permit `Owner` **and** `FinancePayroll` to propose (`tasks.md:67-76`, `services/financial_rules.py:19-26`), but M012 `payroll_rule_approval_guard` checks `current_setting('app.role') = 'Owner'` on every INSERT (`012:307-312`), preventing FinancePayroll PENDING proposals. Approval restriction to Owner is separate and appropriate. Tripwire: with seeded tenant/actor and context set to FinancePayroll, INSERT a valid PENDING `financial_rule_versions` row under `lukla_app`; expect one PENDING row, then FinancePayroll approval denied, Owner approval with evidence accepted; old DDL is predicted to fail the first INSERT with `42501 RULE_APPROVAL_FORBIDDEN`. Do not silently widen approval.
3. **Period validation and mutation gaps [Verified source; predicted runtime failure].** `payroll_periods` only checks `period_start < period_end`, exact-window uniqueness, arbitrary text `timezone`, `time` `cutoff_local` (`009:42-60`). Overlapping non-identical periods, `UTC`, and `12:00:01` satisfy those SQL constraints, unlike phase-3 contract `Asia/Jakarta`, exact `HH:MM:00`, and no overlapping period. M012 grants whole-table `UPDATE ON payroll_periods` (`012:565`) and `payroll_period_transition` (`012:131-151`) checks selected status transitions, not changes to existing period dates, zone, cutoff or rule version; even APPROVED→APPROVED with changed fields passes its explicit predicate. Test as restricted role with seeded real row, not just model validation: reject overlapping insert, invalid zone/cutoff, and post-approval field edits; after failure assert original row unchanged. Prefer a DB CHECK for fixed timezone/whole-minute cutoff, exclusion on tenant/date range if overlaps forbidden, narrow updates/transition checks for mutable fields. Confirm with owner which adjacent-window semantics are intended before adding constraint.
4. **Transaction/session timezone affects period attribution [Verified source plus official PG behavior; not data-fixture reproduced].** M012 `e.passed_at::date` occurs in wage guard, wage SELECT and overhead count (`012:67-81,372-387,439-441`), while the stored `v_period.timezone` and `cutoff_local` are not applied. For `2026-10-01 00:30:00+07`, UTC session date is `2026-09-30`; the factory date is `2026-10-01`. PostgreSQL documents timezone conversion with `AT TIME ZONE` and session-dependent timestamptz interpretation: https://www.postgresql.org/docs/18/functions-datetime.html . On an isolated migrated DB seed one PASS at that instant, verify eligibility/credits under `SET LOCAL TIME ZONE 'UTC'` and `'Asia/Jakarta'` for `[2026-10-01,2026-10-02)`; assert both produce the same factory attribution, and test one event at/after cutoff boundary. Initial read-only server reports `Asia/Bangkok`, not a valid basis for implicit period attribution. Use `AT TIME ZONE v_period.timezone` and explicit cutoff semantics if confirmed by contract, not global session timezone.
5. **Context is not authenticated identity [Verified source + docs; security boundary, not a proven API exploit].** M001 `set_request_context(uuid, uuid, role,...)` is executable by `lukla_app` (`001:62-111`), assigns transaction-local custom settings but verifies no actor–tenant membership/role. M012 `payroll_context_tenant()` checks tenant/actor active and role name, not their association (`012:8-31`); `payroll_approve_rule` and `payroll_advance_run` are definers granted to app role (`012:490-523`). SQL clients holding the pool credential can claim an active other tenant/actor and `Owner` in SQL; no attacker access to that credential or end-user exploit was demonstrated. `backend/app/core/database.py:69-83` relies on an authenticated caller to supply the context; independently verify end-user JWT→context authorization and ensure untrusted clients never receive SQL/pool credential. Test restricted app role and scoped app auth separately; negative control uses FinancePayroll context then attempts Owner-only approval, and controlled forge test uses *only isolated fixture identities* to demonstrate GUC is not an independent identity proof. PostgreSQL documents `set_config(...,true)` transaction locality (https://www.postgresql.org/docs/18/functions-admin.html), SECURITY DEFINER owner privileges and secure `pg_temp` last/default PUBLIC EXECUTE (https://www.postgresql.org/docs/18/sql-createfunction.html), FORCE RLS owner behavior and superuser/BYPASSRLS exemption (https://www.postgresql.org/docs/18/ddl-rowsecurity.html). M012 revokes CREATE on public and sets pg_temp last for its definers (`012:544-563`), but check inherited writable schemas and function owner in the deployed role graph. `SET LOCAL` restores prior session value at transaction end; do not depend on transaction locality as authentication or on rollback to clear a preexisting session-level setting (https://www.postgresql.org/docs/18/sql-set.html).
6. **Pending state/no-write split [Verified source; prior probe is historical].** `calculate_weekly_payroll` raises `FINANCIAL_RULE_PENDING` before monetary inserts (`012:349-366`); exception abort means it cannot simultaneously persist `PENDING_RULE`. Comment at `012:362-365` defers recording pending state to phase 4, with no narrow checked transition API yet. The spec `specs/payroll-engine-runtime/spec.md:20-29` requires both `409` and PENDING_RULE with zero monetary writes. A phase-3 readback test must separately show correct status after commit, or explicitly defer this part and not call phase 3 passed. Historical disposable probe in `impl-phase3-boundary-001.md:37-54` reported pending SQLSTATE/no wage/run row, not pending status. Keep two-transaction status recording scoped and authorized, never turn the exception into a monetary write.
7. **RLS and concurrency require independent probes [Verified source; unverified runtime].** M012 `payroll_read_rows` checks context before a bounded tenant-filtered allowlisted read (`012:464-487`), removes direct SELECT from 21 tables, disables direct app inserts into run/link (`012:529-545`), and sets ENABLE/FORCE RLS; M001/M008 keep separate table privileges and policy expressions, so this does not assert universal empty-table missing-context refusal. The reader returns generic JSON/UUID-ordered pages, not a typed contract list. Weekly routine locks the period before selecting max run version and credits (`012:347-401`); unique original-credit index (`009:96-98`), unique bonus assembly (`009:165-180`), committed-credit unique index (`009:112-126`) protect duplicates but do not themselves prove retry/replay responses or absence of late-credit races. PostgreSQL default READ COMMITTED takes a new snapshot each command, locking/wait behavior and ON CONFLICT outcomes differ from naive sequential reasoning: https://www.postgresql.org/docs/18/transaction-iso.html and https://www.postgresql.org/docs/18/explicit-locking.html . One run/period transaction pair must race concurrently and check the final rows and hashes, not just two serial calls.
8. **Payment/evidence handoff [Verified source; no phase-4/5 demand].** M009 `payroll_payments` requires a UUID evidence_file_id, run FK and unique `(tenant_id,run_id)` (`009:139-152`); M012 checks run status APPROVED at insert (`012:261-270`). It has no FK to an evidence-file table (comment `009:1` says upstream file table absent) and no external transfer proof. Do not claim payments validated end-to-end or invent bank transfer behavior. M008 ledger immutable, late-line, balance triggers are independently owned (`008:86-174,269-272`) and should be tested as restricted-role controls, not rewritten for this change.
