## Findings, ordered by severity

### MAJOR — IR-01 — BLOCKING_DEFECT: missing context can silently return zero or wrong error

`backend/migrations/012_payroll_routines_rls.sql:6-23,277-281,342-346,394-400`; criterion: Tenant-Isolated Payroll Data Access / missing-context refusal. On a fresh, empty payroll database under `SET LOCAL ROLE lukla_app` and **without** request context, `SELECT count(*) FROM payroll_periods` returned `[(0,)]`, `SELECT * FROM payroll_periods` returned `[]`, and `calculate_weekly_payroll(random_uuid(), 'test')` raised `02000 PERIOD_NOT_FOUND`, not `TENANT_CONTEXT_MISSING`. RLS predicates are not guaranteed to execute when there is no matching row, and the routine puts `payroll_context_tenant()` inside the query rather than checking it first. The implementation report's populated-table rejection does not prove the universal read criterion.

**Required change:** enforce explicit request-context validation before every payroll read/routine path, including empty tables; retain tenant isolation and avoid assuming the RLS predicate is an unconditional error hook. **Validation:** repeat these exact no-context empty-table probes under the non-owner role, requiring `TENANT_CONTEXT_MISSING`, plus populated and cross-tenant negative controls. Application request-level enforcement belongs to phase 4 and is not falsely claimed here.

### MAJOR — IR-02 — BLOCKING_DEFECT: paid period can be reopened by the app role

`backend/migrations/009_payroll_core.sql:38-55`; `backend/migrations/012_payroll_routines_rls.sql:275-283,327-329,403`. `payroll_periods` has only a status enum; the broad table UPDATE grant has no lifecycle guard. In disposable PostgreSQL 18.6, as `lukla_app` with a valid Owner context, an inserted `PAID` period was changed to `OPEN` and `UPDATE ... RETURNING status` returned `OPEN`. The payroll routine only refuses recalculation while the current period status is APPROVED/PAID/REVERSED; reopening defeats that test. Existing paid *run* rows remain protected, but the period is not terminal.

**Required change:** enforce period lifecycle transitions at the database write boundary (or remove the direct status grant and provide an equivalently enforced narrow operation), without adding an unapproved business policy. **Validation:** direct non-owner SQL PAID→OPEN and APPROVED→OPEN must fail; permitted forward transitions and approved/paid run immutability must continue to pass.

### MAJOR — IR-03 — BLOCKING_DEFECT: approval accepts a fabricated zero-credit calculation

`backend/migrations/009_payroll_core.sql:57-75,100-115`; `backend/migrations/012_payroll_routines_rls.sql:130-171,403`. `lukla_app` may INSERT arbitrary `payroll_runs` with an arbitrary `input_hash`; insert only checks `status='CALCULATED'` and an approved rule, and the approval transition only rechecks the rule. The AFTER trigger commits whichever credit links happen to exist, including none. In a disposable PostgreSQL 18.6 database, the application role inserted a CALCULATED run with `decode('00','hex')`, approved it, and `SELECT count(*) FROM payroll_run_credits` returned `0`. This bypasses the routine's no-output guarantee (`012:310-313`) and the invariant that approval freezes actual contributing credits and their hash.

**Required change:** prevent direct approval of uncomputed/fabricated runs; pin approval to the genuine calculated input hash and contributing credits at the database boundary (or remove broad direct writes in favor of a guarded transaction). Do not invent a payout value for zero production. **Validation:** repeat the fabricated-run/zero-credit probe, verify rejection; verify real versioned recalculation, hash matching, credit commitment and payment after valid approval.
